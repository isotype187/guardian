# ADR-003: Checkpoint-Before-Change Pattern

**ADR Number:** ADR-003  
**Title:** Mandatory Checkpoint Creation Before Any State Mutation  
**Status:** Accepted  
**Date:** 2026-07-19  
**Authors:** Guardian Engineering Team  
**Reviewers:** Guardian Engineering Team  

---

## Context

Guardian manages critical system state (configuration, checkpoints, events, memory). Any mutation risks data loss or corruption.

## Problem Statement

How to ensure recoverability for all state-changing operations in Guardian?

## Options Considered

### Option 1: Ad-hoc Checkpoints (Developer Discipline)
**Description:** Developers remember to create checkpoints before risky operations.
**Pros:** Flexible; no overhead for read-only ops
**Cons:** Unreliable; human error; no enforcement

### Option 2: Automatic Checkpoint on Every Write (Selected)
**Description:** Wrapper functions automatically create emergency checkpoints before any mutating operation.
**Pros:** Guaranteed safety net; consistent pattern; auditable
**Cons:** Performance overhead (mitigated by tiered checkpoints); storage growth (managed by rotation)

### Option 3: Transactional File System (e.g., NTFS TxF)
**Description:** Use OS-level transactions.
**Pros:** Atomic at filesystem level
**Cons:** Deprecated/removed in modern Windows; not cross-platform; doesn't cover logical consistency

## Decision

**Selected Option:** Option 2 — Mandatory Checkpoint Before Change via Wrapper Pattern

All mutating functions in Guardian follow this pattern:
```powershell
function Set-GuardianSomething {
    param([string]$Value)
    
    # 1. Policy gate
    $policy = Test-GuardianPolicy -Action "modify_something" -Context @{Value=$Value}
    if ($policy.decision -ne 'ALLOW') { 
        Write-GuardianAudit -Action "denied_modify" -Decision $policy.decision
        return $policy.explanation
    }
    
    # 2. Safety checkpoint
    $cp = New-GuardianCheckpoint -Tier Emergency -Label "Pre-Set-GuardianSomething"
    
    try {
        # 3. Execute mutation
        Do-The-Actual-Work -Value $Value
        
        # 4. Success audit
        Write-GuardianAudit -Action "modify_something" -Decision "SUCCESS" -CheckpointId $cp.CheckpointId
    }
    catch {
        # 5. Automatic rollback on failure
        Restore-GuardianCheckpoint -Checkpoint $cp -Confirm:$false
        Write-GuardianAudit -Action "modify_something" -Decision "ROLLED_BACK" -Error $_.Exception.Message
        throw
    }
}
```

## Consequences

### Positive
- Every mutation has a recoverable state
- Audit trail shows checkpoint ID for every change
- Rollback is tested (happens on every failure)
- Consistent pattern across all modules

### Negative
- Checkpoint creation latency (~50-200ms)
- Storage growth (managed by tiered retention: Emergency 30 days)

### Risks Introduced
- **Checkpoint itself could fail** — Mitigated: Checkpoint creation is validated; if it fails, mutation is blocked
- **Emergency tier exhaustion** — Mitigated: Rotation policy (30-day TTL); monitoring alerts on tier capacity

## Alternatives Rejected

Option 1 rejected: Human discipline doesn't scale.
Option 3 rejected: Not portable; deprecated technology.

## Implementation Notes

- `Guardian_Checkpoint` module provides `New-GuardianCheckpoint`, `Restore-GuardianCheckpoint`, `Test-GuardianCheckpointIntegrity`
- Four tiers: Rolling (hourly, 72h), Milestone (per release, forever), Emergency (pre-risk, 30d), Archive (monthly, 7yr)
- All remediation actions in `Guardian_Remediation` use this pattern
- Bridge operations in `Guardian_Bridge` use this pattern
- Self-modification in `Guardian_DriftGuard` uses six-lock guard including emergency checkpoint
