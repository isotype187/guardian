# ADR-001: Separation of Guardian and Nexus98

**ADR Number:** ADR-001  
**Title:** Strict Separation of Guardian (code-level) Separation Between Guardian and Nexus98  
**Status:** Accepted  
**Date:** 2026-07-19  
**Authors:** Guardian Engineering Team  
**Reviewers:** Guardian Engineering Team  

---

## Context

Nexus98 is the creation engine (build, deploy, execute). Guardian is the supervisory intelligence layer (observe, evaluate, protect, recover). Both systems exist in the same workspace but must remain architecturally distinct.

## Problem Statement

How should Guardian and Nexus98 relate at the code/repository/runtime level?

## Options Considered

### Option 1: Single Repository, Shared Runtime
**Description:** Guardian and Nexus98 in one repo, shared PowerShell session, direct function calls.
**Pros:**
- Simple communication
- Easy code sharing
- Single deployment
**Cons:**
- Violates separation of concerns
- Guardian can accidentally modify Nexus98 state
- Single point of failure
- No independent versioning
- Hard to enforce boundaries

### Option 2: Separate Repositories, HTTP/gRPC API
**Description:** Fully separate repos, communicate via network API.
**Pros:**
- Strong isolation
- Independent deployment
- Technology agnostic
**Cons:**
- Operational complexity (two services)
- Network latency
- Serialization overhead
- More infrastructure

### Option 3: Separate Directories, Governed File-Based Bridge (Selected)
**Description:** Same workspace root, separate directory trees, communication via JSONL message bridge on shared filesystem with governance gates.
**Pros:**
- Clear boundary (directory structure)
- No network infrastructure needed
- Human-readable messages (JSONL)
- Governance gates on every message
- Independent versioning via git worktree
- Checkpoint/restore works naturally
- Bridge is auditable and replayable
**Cons:**
- Filesystem coupling (shared volume required)
- Not distributed (single machine)
- Requires discipline to maintain separation

## Decision

**Selected Option:** Option 3 — Separate Directories, Governed File-Based Bridge

Guardian and Nexus98 remain in the same workspace root (`D:\Nexus98_Guardian` and `D:\Nexus98`) but:
1. **No shared runtime** — Separate PowerShell sessions
2. **No direct calls** — All communication via `Guardian_Bridge` JSONL message bus
3. **Governance on every message** — `Test-GuardianPolicy` validates all inbound/outbound
4. **Advisory only** — Guardian→Nexus98 messages are recommendations; Nexus98 decides
5. **Validated intake** — Nexus98→Guardian messages go through schema + permission validation

## Consequences

### Positive
- Clear architectural boundary enforced by directory structure and loader
- Bridge provides audit trail, replay, deduplication, retry
- Governance gates prevent unauthorized actions
- Checkpoint system works naturally (bridge state included)
- No network infrastructure required for MVP

### Negative
- Filesystem coupling limits distributed deployment (Phase 6+)
- Requires shared volume for bridge (not an issue for single-host)
- JSONL parsing overhead (negligible for current message rates)

### Risks Introduced
- **Bridge bypass** — Mitigated: `Guardian_Bridge` dispatcher validates every message; `Guardian_DriftGuard` detects unauthorized module changes
- **Message schema drift** — Mitigated: `Guardian_Contracts` types; contract testing in CI (M11)

## Alternatives Rejected

- Option 1: Violates core principle "Guardian does not replace the systems it protects"
- Option 2: Over-engineering for current scale; introduces operational complexity prematurely

## Implementation Notes

- `Guardian_Env` defines separate root paths
- `Guardian_Contracts` defines all message types with `@odata.type` discriminator
- `Guardian_Comms` handles JSONL persistence (outbox/inbox)
- `Guardian_Bridge` implements dispatcher, dedup, retry, security validation, governance gating
- `Guardian_DriftGuard` monitors for architecture violations

## Future Review

**Review Date:** 2026-12-19 (or when multi-host deployment required)  
**Review Triggers:**

- Nexus98 moves to separate host
- Message throughput exceeds filesystem capacity (>10k msg/s)
